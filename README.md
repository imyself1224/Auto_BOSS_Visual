# auto_boss

用**纯视觉**驱动浏览器，在 BOSS 直聘上自动打招呼（点「立即沟通」）。
背后接 DeepSeek，由它完成所有的视觉定位。

---

## ⚠️ 先读这一段

这个工具会代替你做出**对你账号有真实后果**的操作。用之前请确认你接受：

1. **违反平台协议。** BOSS 直聘《用户协议》明确禁止使用机器人、爬虫、
   "刷屏"软件及注入代码干扰服务。使用本工具属于协议禁止的行为。
2. **存在封号风险。** 社区有明确记录：轻则警告、限制功能，重则**冻结 30 天乃至永久封禁**。
   官方曾在一个半月内处置过两万余个招聘相关账号，并提到过"机器指纹"识别。
3. **每日额度由平台控制**，用尽时会弹提示，程序检测到会立即停机。
4. **建议先小批量试。** 别拿你养了很久、还挂着简历的主号第一次就跑满额度。
5. **建议验完一个职位再放手。** `--limit 1` 是最小验证单位，
   看着它把一个招呼准确发出去，再用默认额度跑。

本项目默认 `dry_run = true`（只筛选、不发送）。想真发必须显式加 `--live`，
而且会再问你一次确认。这是刻意的摩擦，别去掉。

**仅供个人求职自用。别商用，别提高频群发。**

## 它做什么

**只做一件事：点「立即沟通」。**

点了之后，平台会自动发出它自己的招呼语、并附上你的在线简历 ——
这就是 BOSS 上「打招呼」的完整含义。程序到此为止，**后续对话由你自己接管**。

有一个 `send_custom_message` 开关（**默认关闭**），打开的话程序会在点完沟通后
**再进聊天页补发一条 AI 生成的话术**。不建议开：

- 对方会先收到平台招呼语、紧接着又收到一条长消息，观感像群发机器人；
- 那等于程序替你多说了句话，超出了「打招呼」的范围。

关掉它**不影响 DeepSeek 的作用** —— 模型仍然负责这个项目里所有的视觉定位：
找「立即沟通」按钮、读职位卡、读薪资（绕过字体加密）、判断实习还是全职。
那才是它的主要工作。

## 它怎么工作

和常见的"读 DOM + 模拟点击"方案不同，这里**完全不解析页面结构**：

```
   截图  →  叠加归一化网格  →  交给 deepseek-flash  →  拿回坐标  →  CDP 点击
     ↑                                                                    │
     └────────────────────── 循环直到任务完成 ────────────────────────────┘
```

### 为什么走视觉而不是 DOM

不是炫技，是三个具体问题逼出来的：

| 问题 | DOM 方案的后果 | 视觉方案 |
|---|---|---|
| 列表页薪资金额**字体加密**（私有区字符 U+E000–F8FF） | 抓到一堆乱码 | 截图里是正常数字 |
| 「立即沟通」按钮校验 `event.isTrusted` | JS 注入点击被拒，甚至触发封禁 | CDP 的 `Input.dispatchMouseEvent` 产生真实可信事件 |
| 页面结构几乎每月改版 | 选择器一改全废 | 页面怎么改都不影响 |

代价是慢（每个职位 4~8 次模型调用）。对每天几十条的量级可以接受。

### 坐标是怎么保证准的

关键设计是**归一化坐标 + 网格标尺**：

- DeepSeek 服务端会先把图片缩放到约 1300×1300 等效像素
  （见 [Vision 文档](https://api-docs.deepseek.com/guides/vision)）。
  如果让模型直接报像素坐标，一张 1600×900 的截图传上去就已经被缩放了，报回来的数字对不上。
- 所以我们在**页面里**画一层 canvas 网格，刻度直接标注成 0–1000 的归一化值。
  模型"读到"的刻度就是要返回的数字，和图片缩放完全解耦。
- 小目标走**两段式定位**：先粗定位，再把该区域裁出来放大、
  在区域里画更细的网格重问一次。加密网格的刻度依然标注**全局**归一化值，
  所以不需要任何反算。

### 为什么不用 Playwright / Selenium

改用原生 CDP websocket（`websockets` 库），两个原因：

1. **指纹**。Playwright 连上 CDP 后会往每个页面注入自己的 utility script，
   这是很显眼的自动化特征。原生 CDP 不注入任何东西。
2. **target 归属**。实测遇到过 Playwright 的 `page.url` 显示的是 A 标签页、
   而 `new_cdp_session()` 拿到的 session 却打在 B 标签页上的情况，
   导致截图和实际操作对不上。原生 CDP 一个 target 一个连接，不存在这种歧义。

另外，代码**只调用确实需要的 CDP 命令**，刻意不调用
`Runtime.enable` / `Page.enable` / `Debugger.enable` —— 这几个 enable 正是最主流的
CDP 检测点（例如用 `console.log` 的 getter 探针）。
画网格用的 `Runtime.evaluate` 不需要先 enable，不受影响。

### 一个必须处理对的细节：给谁打招呼

推荐流是「**左边卡片列表 + 右边详情面板**」的布局，右侧面板显示的永远是
**当前选中**那张卡片的详情。

程序是按筛选分数挑职位的，挑中的那个人**不一定**就是右侧正显示的那个。
如果不处理，屏幕上那个「立即沟通」按钮属于**别的职位** —— 会打错人。

所以每次打招呼前会：

1. 先点开目标职位的卡片，把右侧详情切过去；
2. 定位「立即沟通」按钮；
3. **核对按钮所属职位与目标是否一致**（模型会读出按钮所在职位的标题），
   不一致就跳过，宁可不发也不打错人。

这个校验在实测中真的拦下过误发，日志长这样：

```
▸ 具身智能导航算法实习生 @ 千寻智能  600-800元/天
  ! 按钮所属「图数据库工程师」与目标「具身智能导航算法实习生」不符，跳过以免打错人
  ✗ 没能确认沟通按钮，跳过这个职位
```

注意它只是**跳过这一个**，整轮继续跑。

### 另一个坑：弹窗选错按钮会闯进聊天页

点完「立即沟通」会弹一个提示框：

```
        标题「已向BOSS发送消息」
        按钮「留在此页」  「继续沟通」
```

两个按钮都能让弹窗消失，但**「继续沟通」会把你带进聊天页**。
只打招呼时应该点「留在此页」。

早期版本用关键词匹配（"继续"、"沟通"）挑按钮，恰好选中了后者 ——
于是每打完一次招呼就闯进聊天页。现在改成让模型直接标注每个按钮
**会不会离开列表页**（`leaves_page` / `stay_click` / `chat_click`），按模式选择。

## 安装

需要 **Python 3.11+**（用到标准库 `tomllib`）和 Edge / Chrome。

```bash
pip install -r requirements.txt      # 只装一个 websockets，其余全用标准库
```

浏览器会自动探测。没装 Chrome 也没关系，Windows 自带的 Edge 是 Chromium 内核，
CDP 完全兼容 —— 本项目的全部开发与测试都是在 Edge 155 上做的。

## 配置

**1. 填 API key**

```bash
cp .env.example .env
```

编辑 `.env`，填入 [platform.deepseek.com](https://platform.deepseek.com/api_keys) 拿到的 key。
（等号两边不要加空格，不要加引号。）

**2. 填你的个人背景** —— `config.toml` 的 `[profile]` 段

**这段目前是占位内容，务必改成你自己的真实经历。**
它是 AI 写文字时唯一的素材来源。找实习的话 `years` 填 0，
`extra` 里建议写上「可实习 X 个月，每周到岗 X 天」—— 实习岗 HR 特别在意这个。

**3. 调职位条件** —— `[source]` / `[search]` / `[job_filter]`，见下节。

## 使用

```bash
python run.py doctor          # ① 自检：配置 → API → 浏览器 → 视觉链路
python run.py login           # ② 扫码登录，登录态存进独立 profile
python run.py greet --limit 1 # ③ 演练一条：看筛选对不对、选中谁（不点击）
python run.py greet --live --limit 1 --yes   # ④ 真发一条，盯着浏览器确认
python run.py greet --live --yes             # ⑤ 按额度连续跑
python run.py greet --auto    # ⑥ 无人值守：投到平台额度用完，出错自动重启
python run.py stats           # 看历史记录

python tests/test_filters.py      # 筛选规则测试
python tests/test_agent_flow.py   # 状态机测试（全打桩，不碰网络）
python tests/test_auto.py         # --auto 重启逻辑测试
```

### 日常使用：双击 `daily_greet.bat`

它就是 `python run.py greet --auto`。不需要盯着：

- **停在平台额度上**：每次点完「立即沟通」都读一遍页面文字，冒出「次数已用完」
  「已达上限」这类提示就停。你在手机上投的那部分本地看不到，所以上限只听平台的；
  `limits.daily_cap` 只是兜底。
- **出错自动重启**：CDP 断线、模型调用失败、页面异常 → 等 60 秒重开一轮，
  最多连续 5 次。已发过的在去重库里，重启不会重复打招呼。
- **这些情况会停下等你**：验证码（人工过掉后重跑）、登录失效（先 `python run.py login`）。
- **日志**：每次运行的完整输出存在 `logs/greet_<时间>.log`，截图在 `shots/<run_id>/`。

想每天自动跑，用 Windows 任务计划程序（每天 9:05 启动，路径按实际改）：

```
schtasks /Create /TN auto_boss /SC DAILY /ST 09:05 /TR "D:\tools\auto_boss\daily_greet.bat"
```

浏览器窗口要保持登录态（独立 profile 会记住），电脑别睡眠。

**第一次务必按 ① → ② → ③ → ④ 的顺序走。** 别跳 ③ 直接实发 ——
`--limit 1` 是最小验证单位。

`doctor` 会把整条链路验一遍，它会实际打开 BOSS 列表页让模型做一次职位识别，
然后打印每个职位识别出的按钮坐标和 confidence：

```
[5/5] 视觉链路（网格叠加 → 截图 → 模型定位）
  ✓ 页面判定    job_list
  ✓ 识别职位    6 个
      · Python 后端开发 @ 某某科技 [立即沟通] btn=(806,321) conf=0.95
  ✓ 截图存档    shots/doctor
```

坐标明显不对、或 confidence 普遍低于 0.6，去 `shots/doctor/` 看存档截图，
网格和页面内容对不对得上，一眼就能看出来。

### 关于 `--live` 的确认

`--live` 会打印一段风险提示并要求你输入 `yes` 确认。
脚本化运行时加 `--yes` 跳过（但这一步就绕过了人工确认，慎用）。

## 找什么职位

配置里的 `[source]` 决定**去哪找**，`[job_filter]` 决定**发不发**。

### `[source]` —— 职位来源

```toml
[source]
mode = "both"                      # 推荐流 → 求职期望标签 → 关键词搜索，依次走
expect_tabs = ["算法工程师(北京)"]  # 「推荐」旁边的求职期望标签

[search]
queries = ["大模型算法实习", "Agent实习", ...]   # 按投递优先级排
```

**为什么要多来源**：推荐流加了「求职类型→实习」之后只有二三十个岗位，翻到页脚就没了，
离平台每天约 150 条的额度差得远。所以推荐流走完接着点求职期望标签，再逐个搜关键词。
每个来源都会重新设「实习」筛选，翻到页脚（连续两次滚不动）就换下一个。
想多投就往 `queries` 里加词；想少投就删。搜出来的岗位照样过全部筛选。

推荐流有个坑值得说明：**它是页面状态，不是 URL 状态**。打完招呼页面会跳去聊天页，
这时候直接 `navigate` 回原地址会掉出推荐流。程序的处理是：进入后先让模型判断
「当前是不是推荐流」，不是就点一下「推荐」入口，并把点完之后**实际**的地址记下来，
后续直接用它 —— 所以这个判断每个职位只会发生一次。

推荐流是无限滚动，不存在"第几页"。程序用一个累积的滚动偏移量渐进下探：
这一屏挑不出合适的了就往下翻，连续 `max_empty_scans` 屏都没有才收工。

### `[job_filter]` —— 筛选规则

分两层，这个区分很重要：

**第 0 层：BOSS 自带的筛选器**（`boss_filters`）

```toml
boss_filters = [
    ["求职类型", "实习"],
]
```

**这一步不能省。** 推荐流默认给的是跟你求职意向匹配的岗位，实际绝大多数是**全职**；
只靠卡片级过滤，结果就是把看到的一条条全滤掉，一条都发不出去。
筛选器负责**把池子换对**，卡片级过滤负责**把个别漏网的挑出去**，
两者是配合关系，不是二选一。

格式是 `[["筛选器名称", "要选的选项"]]`，筛选栏上可用的有：
求职类型 / 薪资待遇 / 工作经验 / 学历要求 / 公司行业 / 公司规模。

> 薪资待遇不在那里设 —— BOSS 给的是固定档位，没法表达"日薪中位≥300"，
> 这个精确条件交给下面的卡片级过滤，它读的是卡上真实数字。

实测筛选条件会进 URL，程序会自动记住新地址，后续直接复用，不再重复点击。

**第 1 层：硬性条件**（不满足就不发，省额度）

| 条件 | 默认 | 说明 |
|---|---|---|
| `require_internship` | `true` | 只要实习岗 |
| `min_daily_wage` | `300` | 日薪下限，**区间取中位数** |
| `require_city` | `"北京"` | 地点不含这两个字就跳过 |
| `allow_unparsable` | `false` | 薪资读不出来（如"面议"）时是否照发 |

**第 2 层：档位 + 地点软排序**（影响先后，档位还能一票否决）

排序分由两块加起来：

```toml
# 模型把岗位跟 resume/kb.md 逐条对比，判成四档。
# 表里没有的档位 = 不打招呼（所以「不可用」不在表里）。
fit_scores = { "最匹配" = 3.0, "次匹配" = 2.0, "可转投" = 1.0 }

# 地点软排序：命中就加分，只影响先后，不排除。
prefer_districts      = ["海淀区", "海淀"]
prefer_district_bonus = 1.0
```

**档位是「能不能投」的判断，交给模型看简历来定** ——
它比对的是职位详情里的实际技术要求，不是标题里的关键词，
所以「大模型训练」和「LLM 工程」这类同义写法不会被漏掉。
判不出可投的档位就不发，跟「读不全职位名就跳过」是一个原则：宁可漏，不错发。

**地点做成软排序而不是硬条件**，是因为很多岗位只写「北京」不写具体区，
硬卡海淀会漏掉一批实际在海淀的好机会。

每屏扫描时，程序给所有通过硬条件的候选打分，**按分数从高到低发**，
而不是从列表第一个开始。

### `[resume]` —— 求职者画像（外接知识库）

```toml
[resume]
kb_path = "resume/kb.md"
```

`resume/kb.md` 是个**你自己维护的普通 markdown 文件**，内容就是
「哪种岗位可以投、优先投哪些」。程序只读它、从不改写它。

每扫描一屏职位，这段文字会被原样拼进提示词，模型据此给每个岗位判档位。
所以**想改投递范围、加岗位族、调优先级，直接改这个文件就行**，下次运行立即生效。

它由你（或让模型读一遍你的简历）一次性写出来即可 —— 简历短期不会变，
没必要让程序每次开浏览器重新识别一遍。项目里不带生成它的代码，是刻意的。

### 薪资是怎么折算的

BOSS 上的薪资写法很杂，一律先折算成**日薪**再比：

| 原始写法 | 折算结果 |
|---|---|
| `400-500元/天` | 400–500，中位 450 |
| `300-400元/天` | 300–400，中位 350 |
| `6-8K` | 月薪 → 276–368，中位 322 |
| `13-26K·14薪` | 先按 14 个月年化，再摊到日 |
| `20-30万/年` | 年薪 → 767–1149 |
| `面议` | 解析不出 → 默认跳过 |

月薪折算日薪用 **21.75** 天（国家规定的月计薪天数，`(365-104)/12`），
由 `work_days_per_month` 控制。实习岗绝大多数直接写「元/天」，这条只在少数岗位生效。

**一个反直觉的点**：`6-8K` 的实习折算下来是 322 元/天、过线；
`5-6K` 折算 253 元/天、会被拒。觉得口径不对就改 `work_days_per_month`。

## 安全阀

这些在 `config.toml` 里：

| 配置项 | 默认 | 说明 |
|---|---|---|
| `limits.daily_cap` | 200 | 本地兜底上限。平台的真实额度约 150/天，用尽会弹提示、程序立即停机 |
| `limits.min_interval_sec` | 25 | 两次打招呼的最小间隔 |
| `limits.max_interval_sec` | 60 | 最大间隔（用三角分布取随机值，比均匀分布更像真人） |
| `limits.max_empty_scans` | 6 | 连续几屏挑不出合适的才收工 |
| `limits.active_hours` | `[9, 21]` | 只在白天跑。凌晨批量操作最容易被标记 |

另外：

- **去重**：按「职位标题 + 公司」做哈希存库，同一个职位绝不重复打扰。
  页面上显示「继续沟通」但本地没记录的，也会记下来跳过。
- **本轮已试过的职位不再重试**，保证循环一定向前推进（否则一个永远失败的职位会导致死循环）。
- **遇到验证码立即停机**，不会尝试绕过 —— 把浏览器窗口交还给你人工处理。
- **配额提示**（「今日主动沟通数已达上限」「开聊次数已用完」）同样立即停机。
- **读不全职位名或公司名的卡片直接跳过**，宁可不发也不能误判去骚扰。
- **按钮所属职位与目标不符就跳过**，不给人打错招呼。
- **CDP 断线会重连**，但只对只读命令自动重试 —— 点击类命令绝不重试，
  因为"第一次其实已经送达"的情况下重试会变成重复点击。

## 排查

**截图是白的 / 是别的页面**
`Page.captureScreenshot` 走的是窗口的可见表面。代码里每次截图前都会
`Page.bringToFront` 激活目标标签。如果你开着多个 Edge 窗口，把别的窗口最小化。

**坐标总是偏一点**
去 `shots/<run_id>/` 看带网格的存档截图。网格线和页面内容对不上，
说明页面 zoom 级别不是 100%（Ctrl+0 复位一下）。

**提示「未能确认立即沟通按钮」**
三种可能：按钮不在当前屏、这个职位已沟通过（按钮变成「继续沟通」了）、
或者**详情面板还停在别的职位上**（这时日志会明确写「按钮所属『XXX』与目标…不符」）。
看存档截图确认。

**筛选器报「点开的是『薪资待遇』不是『求职类型』」**
这一排按钮挨得很近——「求职类型」和「薪资待遇」中心只差半个按钮宽，y 还完全一样，
模型会**自信地**点偏（confidence 0.95），坐标上看不出任何异常。
程序的处理是：点完**核对实际展开的是哪个下拉**，不对就 Esc 关掉重来一次，
并把「上次点成了什么」回喂给下一次定位。连续两次都点偏才放弃，
那一轮退回纯卡片级过滤（不漏发也不误发，但会白扫很多全职岗）。

**「复核坐标在裁剪框外，按局部值换算」**
模型在局部放大图里偶尔会报**裁剪图内部**的相对坐标，无视网格上标的全局刻度。
程序检测到坐标落在裁剪框外就按局部值换算回全局。这条日志出现说明它在工作 ——
没有它的话那一下会点到完全无关的位置。

**模型返回的 confidence 普遍很低**
把 `config.toml` 里 `deepseek.thinking` 设成 `true`。代价是每次调用变慢，
但空间推理会稳一些。

**运行中断在验证码上**
正常行为。人工在浏览器窗口里过掉验证码，然后重跑。
已发过的不会重发（有去重库）。

## 成本

一次完整的视觉定位 ≈ 1 张截图（服务端缩放到约 1300×1300 等效，**封顶 1024 token**）
+ 约 600 token 提示词。实测每个职位约 6 次模型调用、**约 1 万 token**。

按每天 50 条算，量级是**几十万 token/天**。具体单价看
[DeepSeek 定价页](https://api-docs.deepseek.com/quick_start/pricing) ——
这里不写死数字，免得过期。

想省钱可以：调小 `search.pages`、把 `max_empty_scans` 调小、
或者把 `deepseek.thinking` 保持关闭（默认就是关的）。
